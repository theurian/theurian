## What the audit is a population of

An audit is only as good as its key, and a key is a claim: *these are all the
places a control claim can hide.* The key went wrong twice before it held, and
both regressions have the same cause, which is the finding this log exists to
record.

### The three keys, v3

## The closure statement

**v3 is the terminal *achievable* form, not a proof.** The six keys above select
by container and by vocabulary. A claim that sits in none of those containers and
uses none of that vocabulary escapes all of them, and **that escape space cannot
be measured by the keys that define it** — asking whether the census missed
anything, using the census, returns "no" by construction. An earlier revision of
this section did exactly that, and it was circular.

**So the escape space was measured by a third key that shares no rule with the
other six.** It keys on containers the audit never used and on a verb list
deliberately wider than any the audit applied — **58 stems against the sweep's
22**, including `read`, `write`, `name`, `call`, `return`, so that a miss under it
is a claim that is verb-free under *any* plausible key, not merely under mine:

| Independent key | What it selects | Found at `06de58a` |
| :-- | :-- | --: |
| mermaid node labels | a container with no line-opening bold run at all | 2 lines |
| every Markdown table in the document | the whole table population, so the audit's 9 + 2 can be checked against the total rather than trusted | 43 tables, 182 rows |
| headings that themselves assert | entry titles carrying a severity or a claim | 17 |
| prose naming a `src` symbol, **not** bold-opened, carrying **no** verb | the escape space proper | 120 lines |

**No control-capability claim was found escaping.** The 120-line population is
dominated by two shapes that are not claims: **59 of them cite a test path**
(`tests/…::test_…` — evidence for a claim whose head line is a keyed member), and
the remainder are overwhelmingly **line-wrapped continuations** whose subject and
verb sit on the previous line, plus rows of bound tables POP-1b already keys.
That is a real limitation worth naming rather than hiding: **the sweep is
line-oriented, and this document wraps at ~80 columns**, so a claim is routinely
split across a keyed head and an unkeyed tail. What the third key establishes is
that no *head* line escaped — not that no line did.

The 43-table figure is the sharper check, because it is a total rather than a
sample: the audit keyed 11 tables (9 by header pattern + 2 K-2), so **32 tables
went unkeyed**, and the header-pattern key is what says they carry no control
claim. That key is now written down above, which is what makes it attackable.

**One population does live in the escape space, and it is not a capability
claim.** An **owner-cite** — an issue named as owning a residual or a future
control — asserts something about the *tracker*, not about what the codebase can
do, so no key aimed at capabilities was ever going to select it.
`threat-model.md:3820` reads "[#15] removes this face and T-17a's collection
statistics together"; #15 is closed and the residual is live. Found by a parallel
lane after this audit closed, and filed as
[#427](https://github.com/theurian/theurian/issues/427), which sweeps the
owner-cite population on its own stated key. C-2 corrected three owner-cites only
because the *entries* they sat in were keyed members — the audit found them by
where they lived, never by what they claimed, which is why it found three and not
all of them.

**This is the v4 the statement reserves, arriving as designed.** The
control-capability argument stands as measured against an independent key; the
population it never covered now has a name, a key and an owner. A future finding
in the escape space is a named v5 on the same terms — not evidence that the
argument was empty.

### Known limitations of these keys

**A false positive in the 1e key**, found while writing this log: a bold run that
begins a line by accident of *wrapping* is indistinguishable from a block opener.
A sentence in this PR's own T-16 correction wrapped so that `**closed**` started
a line, and the key counted a 22nd discharge block that does not exist. Rewrapped
rather than special-cased — the key is right that a line-opening bold run is how
this document opens a block, and prose that wraps that way is ambiguous to a
human reader too.

**A false negative across all three keys: the owner-cite.** The example is
`threat-model.md:3820`, a continuation line inside a correction blockquote — its
leading `>` markers elided here, because a fenced block whose lines open with `>`
is the one thing `test_flattening_blockquotes_does_not_touch_fenced_content`
exists to forbid, and this log is not worth making `_flatten_blockquotes`
fence-aware for:

```
[#15](https://github.com/theurian/theurian/issues/15) removes this face and
T-17a's collection statistics together, which is the evidence that they are one
class rather than two findings.
```

#15 is `CLOSED COMPLETED` (2026-08-10) and the residual is live, so the sentence
names a closed issue as the owner of an open face — C-2's class, at a site C-2
never reached. Each key misses it for its own reason, and each was measured:

| Key | Why it misses | Check |
| :-- | :-- | :-- |
| Container census | the line is not a bold-labelled block opener — it opens with `[`, not `**` | `grep -cE '^[ \t>]*\*\*[^*]'` on the line → `0` |
| Verb sweep | "removes" is not in the verb alternation, which lists control verbs (`refuses`, `rejects`, `bounds`, …) — an owner-cite uses the vocabulary of *fixing*, not of *enforcing* | the verb regex against the line → no match |
| Structural 1e | **not blind — it reached the text and looked at something else.** The enclosing member opens at `:3701` and was dispositioned on its retraction premise (`Visibility.cleared` has exactly two production callers, verified). Owner liveness was never the axis. | the 1e member list: the last member before `:3820` is `:3701` |

The third row is the instructive one. A key can *cover* a line and still miss the
claim on it, because coverage is about text and a disposition is about a
question. "Which claims did the key reach" and "which questions did the audit ask
of them" are two different completeness arguments, and only the first was written
down here. Owned by [#427](https://github.com/theurian/theurian/issues/427).

## The meta-finding

**Four enumeration misses in this arc share one root cause: a key chosen by what
its author expected to find.**

1. v1's `**Controls` prefix missed `**Control, part A/B`, by one character.
2. v1's key reached no `*Future controls, not shipped:*` paragraph, where C-1 lives.
3. v1's key reached no `> **Corrected …` blockquote, where C-3 lives — the
   highest-risk text in the document, since a correction block is written to
   replace a falsified premise and then never re-derived.
4. The verb sweep, proposed as the primary key, would have missed `:4940` outright.

The defense is not a more careful reader. It is **a mechanical key run to
exhaustion, plus a stated key that a second reader can attack.** The
census-plus-sweep pair is that defense by construction: the census is mechanical
and total over containers, the sweep is orthogonal to it, and both are written
down here in a form that can be re-run and disagreed with.

The corollary the corrections themselves demonstrate: **a premise that has to
stay true belongs in a test that reddens, not in a sentence.** C-1's conclusion
survives because
`test_the_shipped_modules_that_name_a_watched_config_key_are_the_recorded_ones`
pins the reader set as an equality over the whole source tree. C-3's premise had
no such pin, which is why a correction block written to fix a wrongly-named
mechanism went stale the same way within one milestone.

## M-1 — YAML alias expansion cost in `projection._walk`

Owed by #199's body: `MAX_DEPTH` bounds depth, and breadth via YAML aliases was
recorded as unmeasured, with the guess that `_StrictLoader`'s node cache bounds
it.

**Measured answer: the loader's node cache does not bound the walk.** `_walk`
carries no memo — unlike `_external_refs`'s `descended` — so a node reached by
*n* paths is entered *n* times. Within the projection, what stops it is
`MAX_PROJECTION_CHARS`, charged in `_Spend.emit` *during* the walk, not
`MAX_PROJECTION_NODES`.

**That answer is true and was not the question T-6 needed answering.** The
projection is ~6% of what ingestion spends on such a document; the YAML parse is
the rest, and `MAX_YAML_BYTES` is the bound that governs it. The section below
records how a correct narrow finding was reported as a wrong broad one.

### The first measurement was wrong three ways, and the round found all three

**The figures this section originally carried are withdrawn, not adjusted.** They
were reported to the threat model as an ingestion-path cost and were none of the
things that phrase means. Recorded here in full because the *shape* of the error
is more reusable than the number:

| What was measured | What ingestion actually does | Effect on the figure |
| :-- | :-- | :-- |
| `project_checked`, which **raises** on a budget | `project`, which **truncates** and indexes the result (`ingestion_service.py:225`) | measured a function with no production caller at all |
| wall clock **under `tracemalloc`** | — | inflated 6.4–7.6× |
| the projection **alone** | parse **then** project | omitted the term that dominates (94% at the gate's ceiling) |

Compounding: a ~3.1 s "ingestion-path" figure against a real clean end-to-end
cost of 2.27 s on that document — and the real *worst* case, on the widest
document the gate admits, is 6.32 s, which the original never looked at because
it had stopped at the document the *projection* was slowest on.

The withdrawn comparison is the sharpest lesson. It said the alias shape cost
~6.5× the 0.48 s `projection.py::MAX_PROJECTION_NODES` records. That put an
instrumented number against a clean one:

```
amendment said: worst alias 3.14 s is ~6.5x the node-ceiling 0.48 s
clean/clean   : 0.379 s vs 0.397 s  ->  0.95x
traced/traced : 2.844 s vs 2.976 s  ->  0.96x
traced/clean (what the amendment did): 2.844 s vs 0.397 s -> 7.16x
```

Clean on clean the two shapes are indistinguishable, so the comparison is not
restated in a corrected form — **it never had a finding in it.** A ratio between
two numbers taken on different instruments is not a weak measurement; it is not a
measurement.

### The second measurement had a frame error too, and it was the label

The re-measurement above was reported with the frame "CPython 3.12.2" — taken
from a bare `python3 -c` call rather than from the measuring process. On this
machine bare `python3` is mise's **3.12.2** while `uv run --frozen python` is
**3.13.3**, and the package requires >=3.13. The script had run under
`uv run --frozen`, so the *numbers* were from 3.13.3 and only the *label* was
wrong — but nothing in the record said so, and a reviewer reading the label
attributed a later 2× disagreement to the interpreter.

**Both interpreters were then measured explicitly**, frame self-reported from
inside each process:

```
alias fan, widest under gate   CPython 3.12.2   TOTAL  6.978s   RSS +179.0 MB
alias fan, widest under gate   CPython 3.13.3   TOTAL  6.178s   RSS +178.7 MB
block seq `- 1`, widest        CPython 3.12.2   TOTAL 14.226s   RSS +664.2 MB
block seq `- 1`, widest        CPython 3.13.3   TOTAL 13.064s   RSS +666.2 MB
```

**The interpreters agree within ~12%, with 3.13 marginally faster in both cases,
and RSS identical to three significant figures.** The 2× that was attributed to
the interpreter is the gap between two *document shapes* — 13.06 s against
6.18 s — measured on the same interpreter. Right observation, wrong cause: the
familiar shape.

Two lessons, both cheap and both learned the expensive way here:

- **A measurement frame is part of the measurement.** Read it from the process
  doing the work — `platform.python_version()` printed by the script — never from
  a command typed beside it. A wrong label is not cosmetic; it is what a later
  reader reasons *from*, and here it manufactured an interpreter theory.
- **`ru_maxrss` is a process high-water mark.** Measuring four shapes in one
  process reported `+0.0 MB` for a shape that costs ~596 MB, because an earlier
  shape had already raised the mark. One shape per process, or the memory column
  is fiction.

### Re-measured: the shipped path, one shape per process

`YamlParser.parse` → `project`, on **CPython 3.13.3 arm64** (self-reported),
`projection.py`, `yaml_loading.py` and `ingestion_service.py` identical to
`main`. Wall clock clean; python-heap peak taken in a separate pass and labelled.

```
alias_small    1,289,309 B | parse   1.807s | project  0.373s | TOTAL   2.180s | parse share 82.9% | RSS +  81.9 MB | TRUNCATED+indexed
alias_fan      4,194,295 B | parse   5.802s | project  0.376s | TOTAL   6.178s | parse share 93.9% | RSS + 178.7 MB | TRUNCATED+indexed
flat_scalars   4,194,280 B | parse  10.272s | project  0.125s | TOTAL  10.397s | parse share 98.8% | RSS + 595.7 MB | TRUNCATED+indexed
block_seq      4,194,291 B | parse  12.961s | project  0.103s | TOTAL  13.064s | parse share 99.2% | RSS + 666.2 MB | TRUNCATED+indexed
```

**The worst shape found moved again**, from the alias fan to a block sequence of
`- 1` entries: 4 bytes per node, ~1.05 million nodes in 4 MiB. **Token density,
not alias structure, is the lever** — which strengthens the entry's conclusion
rather than complicating it, since `MAX_YAML_BYTES` is precisely the bound that
governs token count. `_StrictLoader` derives from PyYAML's pure-Python
`SafeLoader`, not `CSafeLoader`, so the parse is interpreted per-token work and
libyaml never enters this path on either interpreter.

Conclusions, each carrying its number:

1. **The structural finding survives the re-measurement.** `_walk` carries no
   memo, so a node reached by *n* paths is entered *n* times: at 22 alias levels
   the parsed graph holds **48** objects while the walk enters **120,491**. Visit
   counts are instrument-independent, which is why this half stood while every
   timing beside it fell.
2. **The projection is not where the money goes.** `MAX_PROJECTION_CHARS` does
   bind the walk rather than `MAX_PROJECTION_NODES`, but the walk is **under 3%**
   of end-to-end cost on the worst shape. **`MAX_YAML_BYTES` is the bound that
   matters for T-6's ingestion cost**, and the original amendment never named it.
3. **The shipped path admits the document.** `project` truncates at
   `MAX_PROJECTION_CHARS`, appends `SIZE_MARKER` and returns the text to be
   indexed. Nothing refuses. "Refused" appeared throughout the first measurement
   because `project_checked` refuses — and nothing calls it.
4. **Residual, MEDIUM:** ~13 s single-threaded CPU-bound work and ~666 MB RSS
   for one clone-reachable document, after which a truncated projection is
   indexed. Availability, not disclosure; ingestion-side, so #26 (query-side)
   does not own it. **This is the worst shape *found*, not an established
   maximum** — no exhaustive search over document shapes was run, and the figure
   has now moved twice under search, from 2.27 s to 6.18 s to 13.06 s. Each move
   came from someone trying a shape nobody had tried, which is the honest reading
   of "worst found": a lower bound on the maximum, not the maximum. T-6's
   recorded decision that no ingestion-side timeout is filed is unchanged.
